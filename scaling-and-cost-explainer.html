00

How the service is built today

The service is a single HTTP endpoint. A caller sends it a video URL; it returns the extracted chunks. Behind that door, the real work runs as a durable workflow — a background job that keeps running even if the request disconnects or a server restarts. The algorithm itself (audio slicing, transcription, tagging, vision) lives in framework-free modules, separate from anything Next.js-specific.

01

Do we need to rewrite from Next.js to Python?

✓

No rewrite needed

The language is not the bottleneck. The heavy work is external API and ffmpeg calls that run identically in any language — Python would not make them faster.

It helps to see where the work actually happens. "Next.js" is only the doorway. The algorithm already lives in plain, framework-free modules. The workflow file even says so directly:

"All domain logic lives in the orchestration-agnostic src/lib/pipeline/* modules, so moving off this host later means swapping one file, not the pipeline." — src/workflows/transcribe-video.ts

Keep Language & framework
  • Pipeline is already isolated and portable
  • The workflow engine gives durability for free
  • A rewrite is weeks of risk for zero speed gain
Ignore The Python idea
  • Won't speed up Whisper / GPT / Vision calls
  • Won't reduce cost per video
  • Scaling is an infrastructure question, not a language one

What "scale" actually means here: running more videos in parallel. That is solved by running more workers / more workflow concurrency and respecting the transcription rate limits — the same answer in any language.

02

What happens to a 4–5 hour video that takes 30+ minutes?

✓

Already handled — the job never dies with the request

The processing runs in the durable workflow, not in the HTTP request. When the wait runs long, the API returns 202 "still running" and the caller simply asks again later with the same resourceId.

The fear — "the API closes after 30 minutes and we lose the work" — mixes up two separate things: the HTTP connection (short-lived) and the job (durable). They are not the same.

Why this is safe, in the code

  • Job outlives the request: the route calls start(transcribeVideoWorkflow, …) — a background job, not inline work. route.ts:99
  • Graceful timeout: after WAIT_MS (default 25 min) it returns 202 instead of hanging until a proxy kills it. route.ts:36, 118–127
  • Idempotent re-call: an existing resourceId is never reprocessed; it attaches to the in-flight run or returns the finished result. route.ts:53–56
  • Streams, never downloads the whole file: ffmpeg range-reads each small slice, so even 4-hour videos stay within the small /tmp budget. transcribe-video.ts:1–7
  • Paces around rate limits: a transcription 429 becomes a retryable wait, up to 25 retries per chunk — built for multi-hour videos. transcribe-video.ts:114, 133
!

The one thing to confirm on the caller side

The calling service must treat 202 as "not done, poll again," not as success and not as failure. If it already polls, long videos need no code change at all. This is a contract to verify, not a rewrite.

03

What the pipeline actually does (and where the money goes)

Each stage is a durable step. Two of them cost money on every video: transcription (Whisper) and the language + vision steps (GPT-5.4 and Vision). The rest is ffmpeg and bookkeeping.

04

How much does one video cost in API credits?

Cost has two buckets. One is predictable, one is variable.

Bucket A — Whisper transcription (predictable)

Whisper (whisper-1) bills per minute of audio, for the whole video, at about $0.006 / min. This is the part we can state exactly:

Bucket B — GPT-5.4 text + Vision (variable)

These steps scale with how much was said and how many chapters the video has, not with raw minutes. A talkative 30-minute repair video with many chapters can cost more here than a quiet 60-minute one. Vision (image) calls are the most expensive single item. This bucket is usually larger than Whisper, and it can only be pinned down exactly by measuring real token usage — the code has the numbers, we just do not log them yet.

To turn estimates into exact numbers: every OpenAI response already returns a usage object. Logging it in src/lib/pipeline/openai.ts would give real per-video cost with no guesswork. This is the one small change worth making before scaling up.

05

Takeaways

  • Keep Next.js. The algorithm is already portable and language-independent; a Python rewrite buys no speed and no cost saving.
  • Long videos are already safe. The workflow is durable and outlives the request; 202 + re-call with the same resourceId is the built-in path for multi-hour jobs.
  • Verify the caller polls on 202. This is the single behavioural contract to confirm — no rewrite involved.
  • Cost is mostly GPT + Vision. Whisper is ~$0.006/min and predictable; the variable bucket is bigger and worth measuring.
  • Next step: log the usage object to get exact per-video cost before scaling.
